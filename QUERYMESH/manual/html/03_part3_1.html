3.0 One analogy for the whole project: a research library with a team of specialists

3.1 Vectors and embeddings: "meaning as a list of numbers"

An embedding model reads a piece of text and returns a list of numbers (a vector). Our model, Jina jina-embeddings-v5-text-small, returns 1024 numbers for any text [17][18]. Texts with similar meaning get vectors that point in a similar direction, even when they use different words.

Example: "car crash" and "vehicle collision" share no words, but their vectors are close. A keyword search would miss this; a vector search finds it.

How close two vectors are is measured with cosine similarity: 1.0 means the same direction (same meaning), 0 means unrelated. We ask Jina for "normalized" vectors (length 1), which makes this comparison fast and fair.

Asymmetric tasks: Jina embeds a question and a passage slightly differently. We send task retrieval.passage when we store paper chunks and task retrieval.query when we embed the user's question. Mixing them up makes search worse.

1-minute check: why would vector search find a paper about "LLM hallucination" when you ask about "models making up facts"? Answer: the meanings are close, so the vectors are close, even with no shared words.

3.2 BM25: "exact words, weighted cleverly"

BM25 is the classic keyword-ranking formula that OpenSearch uses by default for text fields. In plain words, a chunk scores higher when:

  • it contains your query words, and contains them several times (but the 10th repetition adds much less than the 2nd);
  • the words are rare in the whole collection (the word "ColBERT" is worth far more than the word "model");
  • the chunk is not extremely long (long chunks naturally contain more words, so they are slightly penalised).

BM25 is excellent for exact names, acronyms, model names and numbers (for example "RRF", "Qwen3", "BM25", "2401.15884"). Vector search is weak at those. Vector search is excellent at paraphrases. That is why we use both.

1-minute check: you search "DPO". Which search is more reliable, BM25 or vector? Answer: BM25, because DPO is a rare exact acronym.

3.3 Hybrid search and Reciprocal Rank Fusion (RRF), with a worked example

Hybrid search runs BM25 and vector search on the same question and merges the two ranked lists into one. The problem: their scores are on different scales (a BM25 score might be 14.2, a cosine score 0.83), so you cannot simply add them.

RRF solves this by ignoring the scores and using only the positions (ranks) [19]. Each list gives a document 1 / (k + rank) points, where k is a constant (we use the default rank_constant = 60 [15]). The points from both lists are added.

Worked example. Question: "how does RRF merge rankings?". Each search returns its top 3:

PositionBM25 listVector list
1Paper APaper B
2Paper BPaper D
3Paper CPaper A

Now compute the RRF score of each paper with k = 60:

PaperFrom BM25From vectorRRF totalFinal rank
A1/(60+1) = 0.0163931/(60+3) = 0.0158730.0322662
B1/(60+2) = 0.0161291/(60+1) = 0.0163930.0325221
C1/(60+3) = 0.015873not in list = 00.0158734
Dnot in list = 01/(60+2) = 0.0161290.0161293

What to notice:

  • Paper B wins although it was first in only one list: being high in BOTH lists beats being first in one.
  • Papers that appear in only one list (C, D) still get a place, so no good result is lost.
  • A bigger k (for example 100) makes the differences between ranks smaller; a smaller k (for example 10) gives the top positions more weight. Part 7 lets you measure this.

In OpenSearch this is two pieces: a hybrid query that holds the BM25 query and the k-NN query [14], and a search pipeline with the score-ranker-processor set to rrf that does the merging [15]. You create both in Part 4.

1-minute check: Paper E is 2nd in BM25 and 2nd in vector. Paper F is 1st in BM25 and missing from vector. Which ranks higher? Answer: E (1/62 + 1/62 = 0.032258) beats F (1/61 = 0.016393).

3.4 Chunking: "cut the paper into index cards"

A research paper is 10 to 40 pages. An embedding of a whole paper would be a blurry average of everything in it, and the LLM could not read 30 papers at once anyway. So we cut each paper into chunks of about 1,500 characters (roughly 250-350 words).

QueryMesh's chunker works in two steps:

  • First it splits the Markdown that Docling produced at headings (#, ##, ###), so a chunk does not mix the end of "Method" with the start of "Results".
  • Then it cuts long sections into windows of 1,500 characters that overlap by 200 characters, so a sentence on the border is never lost.
  • It drops the References section, because a list of paper titles confuses search.

Docling's job comes before this: a PDF stores letters at x/y positions, not paragraphs. Docling reads the page layout (columns, headings, tables) and returns clean Markdown [12].

1-minute check: why the 200-character overlap? Answer: a fact that sits across the cut appears whole in at least one of the two chunks.

3.5 RAG versus agentic RAG

RAG (retrieval-augmented generation) = search first, then let the LLM answer using only what was found. Plain RAG is a straight line:

question -> search -> top chunks -> LLM writes answer -> done

The weakness: if the search returns bad chunks, the LLM still writes something, often a confident wrong answer (a hallucination).

Agentic RAG adds checks and loops, so the system can notice a bad step and try again [45]:

question -> retrieve -> grade the chunks
   enough relevant chunks?   no -> rewrite the query -> retrieve again (max 2 times)
                             still no -> scout fetches fresh arXiv papers -> retrieve again
   yes -> write the answer with [n] citations -> critic checks it
   grounded?                 no -> writer tries again with the critic's feedback (max 2 times)
   yes -> final answer

This is the "retrieval -> grading -> generation -> retry loops" line of the project. The ideas come from research such as Self-RAG and Corrective RAG [45]. The loop limits (2 retrievals, 2 generations) stop the system from looping forever and burning money.

3.6 LangGraph in four words: state, nodes, edges, Command

LangGraph is a library for building programs as a graph of steps with shared memory [20].

LangGraph wordPlain meaningIn QueryMesh
StateA Python dictionary that every step can read; its shape is declared with a TypedDictQueryState: question, search_query, chunks, relevant, answer, citations, grounded, feedback, attempt counters, steps
NodeA Python function that receives the state and returns only the keys it wants to changesupervisor, retriever, grader, writer, critic, scout
EdgeA fixed arrow: after node X always go to node Yevery worker has an edge back to the supervisor
CommandA node's return value that says "update these keys AND go to that node next"the supervisor returns Command(goto="grader")
ReducerA rule for merging a key instead of overwriting itsteps uses operator.add, so every agent's log line is appended

Why a TypedDict? It documents exactly which keys exist, so a typo like "chunck" is easy to spot, and every agent agrees on the same names. This is the "shared TypedDict state" of the project.

1-minute check: the grader returns {"relevant": [...], "steps": ["grader: 3 of 8"]}. What happens to "steps"? Answer: the new line is appended to the old lines (reducer), it does not replace them.

3.7 Supervisor-worker: one boss, five specialists

In a supervisor-worker design, workers never talk to the user and never decide the overall plan. They do one job and report back. The supervisor reads the shared state after every job and picks the next worker [46].

Our supervisor is a small set of plain rules (no LLM needed for routing), which makes it predictable and easy to test:

What the notebook saysSupervisor sends to
nothing retrieved yetretriever
chunks found but not gradedgrader
at least 2 relevant chunkswriter
fewer than 2 relevant and fewer than 2 searches doneretriever again, with a rewritten query
still not enough and no scout yetscout, then retriever again
answer written, not checkedcritic
critic says not grounded and fewer than 2 draftswriter again, with the critic's feedback
otherwiseEND (return the answer)

Why rules instead of an LLM router? A 4-billion-parameter model sometimes picks the wrong next step; rules never do. The LLM is used where language skill matters: grading, writing, checking, rewriting the query.

3.8 MCP versus A2A, and what SSE is

Both are open protocols, but for different relationships:

ProtocolRelationshipWhat travelsQueryMesh use
MCP (Model Context Protocol) [24]a client calls a TOOL on a servertool name + JSON arguments, JSON resultthe supervisor calls retrieve, grade, write, critic, scout on the five agent servers
A2A (Agent2Agent) [25]an AGENT asks another AGENT to do a taska message, a task with a status, an artifact (the result)the retriever asks the scout for help when it finds too few chunks

SSE (Server-Sent Events) is a simple way for a server to keep an HTTP connection open and push messages to the client as they happen. FastMCP serves each agent's tools over SSE at http://AGENT:PORT/mcp/sse [23]. Our API also uses SSE at /ask/stream to push each agent step to the Gradio page and the Telegram bot while the work is happening.

In one sentence: MCP is how a boss uses a tool; A2A is how two colleagues hand work to each other.

3.9 Agent Cards, agent discovery and peer delegation

Every A2A agent publishes a small JSON "business card" at a fixed address: http://AGENT:PORT/.well-known/agent-card.json [25]. It holds the agent's name, a description, the URL where it accepts A2A messages, and its skills (for example the skill id "scout").

Agent discovery = instead of hard-coding "the scout lives on port 8105", a program reads the cards of all known agents and finds the one that offers the skill it needs. QueryMesh does this twice:

  • the supervisor reads all five cards and builds a map "skill -> MCP address" (retrieve -> http://localhost:8101/mcp/sse, and so on);
  • the retriever, when it finds fewer than 3 chunks, searches the cards for the skill "scout" and sends that agent an A2A message: "fetch fresh papers about this topic". That is peer delegation: one worker asking another worker directly, without going through the supervisor.

Benefit: you can move an agent to another machine or port, update its card, and nothing else changes.

3.10 The SHA-256 exact-match cache

Asking the five agents costs 5-30 seconds and GPU time. If the same question comes again, we can return the stored answer in milliseconds.

How the key is made: the question is lower-cased and repeated spaces are removed, so "What is RAG?" and "what is rag?" become identical. The model name is put in front (a new model must not reuse old answers). This text goes through SHA-256, which turns any text into a fixed 64-character fingerprint, for example querymesh:answer:9f86d08... Same text = same fingerprint, always; different text = different fingerprint.

The answer is stored in Upstash Redis (a hosted key-value database with a free tier [28]) for 24 hours (TTL = time to live). "Exact-match" means only the same normalised question hits the cache; a re-worded question goes to the agents again. That is a deliberate, safe choice: it never returns an answer to a different question.

1-minute check: will "What is RAG" and "What is RAG?" hit the same cache entry? Answer: no, the question mark is a different character, so the fingerprint is different.

3.12 JWT login in plain words

A JWT (JSON Web Token) is a small signed text, for example eyJhbGci... It contains claims such as "sub": "admin" (who) and "exp" (when it expires, 60 minutes for us), and a signature made with our secret JWT_SECRET [31].

Flow: you send your username and password once to POST /token, the API returns a JWT, and every later request carries it in the header Authorization: Bearer YOUR_TOKEN. The API checks the signature and the expiry; it never needs to look anything up. Anyone who changes one character of the token breaks the signature and gets 401 Unauthorized.
