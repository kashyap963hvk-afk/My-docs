PART 7 - ELITE: measure QueryMesh like a research lab, then harden it like a production team

7.0 Who defines the top level today

What: beginners check "does it answer?". Professionals measure HOW WELL each part works, change one thing at a time, and keep the numbers. Researchers publish the methods everyone else then copies. This part shows who they are and gives you a hands-on version of their main method: an evaluation harness that scores retrieval and the whole agent pipeline.

Why: without numbers you cannot tell whether hybrid search, the grader or a new chunk size helped. With numbers you can defend every design choice in an interview ("hybrid raised hit@5 from 0.63 to 0.80 on 30 questions").

When: after Part 6A (the agents work). You do not need EKS for this part; everything runs on the Hyperstack VM.

What the top teams do differently (and you will do now):

  • They build a test set BEFORE tuning, and never tune on the final test questions.
  • They score each stage separately (retrieval, grading, generation) and the whole pipeline.
  • They change ONE setting per experiment and write every result in a table.
  • They report the number of questions and treat small differences as noise.
  • They keep the evaluation in CI, so a change that makes answers worse is caught before deploy.

SECTION 7.1 - Create querymesh/evaluate.py

WHERE: VS Code connected to the VM, Explorer, folder ~/querymesh/querymesh

GOAL: one script with three commands: build a test set, compare search modes, measure the full agent pipeline.

Step 1. Create the file querymesh/evaluate.py with the procedure from Section 2B.3.

Step 2. Paste this content and press Ctrl+S:

"""Measure QueryMesh like a research lab: retrieval quality per search mode, then end-to-end.
  python -m querymesh.evaluate build --n 30     (make a test set from your own index)
  python -m querymesh.evaluate retrieval        (BM25 vs vector vs hybrid: hit@5 and MRR)
  python -m querymesh.evaluate e2e --n 10       (full agents: grounded rate, citation hit, latency)
"""
import argparse
import asyncio
import json
import random
import statistics
import time
from pathlib import Path

from querymesh import config, search
from querymesh.embeddings import embed
from querymesh.graph import ask
from querymesh.llm import get_llm

EVAL_FILE = Path("data/eval.jsonl")


def build(n: int) -> None:
    """Pick random chunks and let the LLM write one question each chunk answers."""
    hits = search.client.search(index=config.INDEX_NAME, body={
        "size": n, "_source": ["paper_id", "title", "text"],
        "query": {"function_score": {"random_score": {"seed": 42, "field": "_seq_no"}}}})["hits"]["hits"]
    EVAL_FILE.parent.mkdir(parents=True, exist_ok=True)
    with EVAL_FILE.open("w") as out:
        for hit in hits:
            chunk = hit["_source"]
            question = get_llm(0.3).invoke(
                "Write one specific question that this passage from a research paper answers. "
                "Do not mention 'the passage' or 'the paper'. Return only the question.\n\n"
                f"{chunk['title']}\n{chunk['text'][:1500]}").content.strip()
            out.write(json.dumps({"question": question, "paper_id": chunk["paper_id"]}) + "\n")
    print(f"wrote {n} questions to {EVAL_FILE}")


def load() -> list[dict]:
    return [json.loads(line) for line in EVAL_FILE.open()]


def run_mode(query: str, mode: str, k: int) -> list[str]:
    if mode == "hybrid":
        return [h["paper_id"] for h in search.hybrid_search(query, k)]
    if mode == "bm25":
        body = {"size": k, "query": {"multi_match": {"query": query, "fields": ["title^2", "text"]}}}
    else:
        body = {"size": k, "query": {"knn": {"embedding": {"vector": embed([query], "retrieval.query")[0], "k": k}}}}
    body["_source"] = ["paper_id"]
    return [h["_source"]["paper_id"] for h in search.client.search(index=config.INDEX_NAME, body=body)["hits"]["hits"]]


def retrieval(k: int = 5) -> None:
    rows = load()
    print(f"{'mode':8} hit@{k}  MRR   (n={len(rows)})")
    for mode in ("bm25", "vector", "hybrid"):
        hit, reciprocal = 0, 0.0
        for row in rows:
            ranked = run_mode(row["question"], mode, k)
            if row["paper_id"] in ranked:
                hit += 1
                reciprocal += 1 / (ranked.index(row["paper_id"]) + 1)
        print(f"{mode:8} {hit / len(rows):.2f}   {reciprocal / len(rows):.2f}")


def e2e(n: int) -> None:
    rows = load()[:n]
    grounded, cited, seconds = 0, 0, []
    for row in rows:
        start = time.perf_counter()
        result = asyncio.run(ask(row["question"]))
        seconds.append(time.perf_counter() - start)
        grounded += bool(result.get("grounded"))
        cited += any(c["paper_id"] == row["paper_id"] for c in result.get("citations", []))
    print(f"grounded rate      {grounded / n:.2f}")
    print(f"cites gold paper   {cited / n:.2f}")
    print(f"latency p50 / max  {statistics.median(seconds):.1f}s / {max(seconds):.1f}s")


if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("command", choices=["build", "retrieval", "e2e"])
    parser.add_argument("--n", type=int, default=30)
    args = parser.parse_args()
    {"build": lambda: build(args.n), "retrieval": retrieval, "e2e": lambda: e2e(args.n)}[args.command]()

SECTION 7.2 - Build the test set

WHERE: VS Code Terminal, folder ~/querymesh, .venv active, vLLM and OpenSearch running

GOAL: data/eval.jsonl with 30 questions, each linked to the paper that answers it.

Step 1. Activate the environment:

cd ~/querymesh && source .venv/bin/activate

Step 2. Make the index big enough to be a real test (40 more papers, 20 to 40 minutes, Docling on the GPU):

python -m querymesh.ingest --query "cat:cs.CL AND abs:retrieval" --max-papers 40

You should see: lines indexed XXXX.XXXXX: NN chunks ..., then a dictionary with "added".

Step 3. Count the chunks in the index:

curl -s localhost:9200/arxiv-chunks/_count | jq .count

You should see: a number above 1000 (it depends on the papers).

Step 4. Build 30 questions (about 1 minute):

python -m querymesh.evaluate build --n 30

You should see: wrote 30 questions to data/eval.jsonl

Step 5. Read three of them:

head -3 data/eval.jsonl | jq

You should see: objects like {"question": "Which fusion method ...?", "paper_id": "2510.01234v1"}.

Step 6. Freeze the test set: copy it, and never edit the copy:

cp data/eval.jsonl data/eval_frozen.jsonl

Watch out: questions written FROM a chunk often reuse the chunk's exact words, which favours BM25. Top teams also write some questions by hand in their own words. Open data/eval.jsonl in VS Code, rewrite 5 questions in different words, save, and say so in your results.

Watch out: random chunks are sometimes a table or an author list. Delete lines whose question makes no sense (VS Code: put the cursor on the line, press Ctrl+Shift+K, then Ctrl+S).

CHECKPOINT: wc -l data/eval.jsonl prints 30 (or fewer after deleting bad lines; keep at least 25).

If not: index_not_found_exception = the index name differs: check INDEX_NAME in .env.

How to read the result:

If you see...It means...Do this next
hybrid is best on both numbersthe two methods find different good papers and RRF combines themkeep hybrid (the normal case)
bm25 clearly beats vectoryour questions reuse the papers' words (see Watch out in Section 7.2)rewrite more questions in your own words, then measure again

SECTION 7.5 - Tuning experiments (one change at a time)

WHERE: VS Code (editor + Terminal), folder ~/querymesh

GOAL: improve hit@5 / MRR with controlled experiments, the way a research lab does.

The procedure for EVERY experiment:

Step 1. Write down the experiment name and the one setting you change in results.md.

Step 2. Make the change (table below says where).

Step 3. If you changed search.py PIPELINE_BODY, update the pipeline in OpenSearch:

python -m querymesh.search setup

Step 4. Run the measurement:

python -m querymesh.evaluate retrieval

Step 5. Paste the result next to the experiment name.

Step 6. Undo the change if the result is not clearly better (difference larger than about 0.07 on 30 questions).

ExperimentWhereChangeWhat usually happens
A rank constantquerymesh/search.py, PIPELINE_BODY"rank_constant": 60 to 20the top results of each list count more; can help when one method is strong
B more vector candidatesquerymesh/search.py, hybrid_search"k": k * 5 to k * 10the vector side considers more chunks before fusion; small gain, a bit slower
C fewer results for the agents.envTOP_K=8 to TOP_K=5less text for the grader and writer: faster, sometimes misses the gold chunk
D smaller chunksquerymesh/ingest.pyCHUNK_CHARS = 1500 to 800, OVERLAP_CHARS = 200 to 150more precise matches; needs re-indexing (see below)
E stricter grading.envMIN_RELEVANT=2 to 3more rewrites/scouting, better grounded rate, higher latency (measure with e2e)
F contextual chunks (Anthropic [46])querymesh/search.py, index_chunksembed the title, the section heading and the chunk text (one per line) instead of title + textchunks are easier to find; needs re-indexing

Re-indexing after D or F (deletes the index, then loads the papers again):

curl -s -X DELETE localhost:9200/arxiv-chunks && python -m querymesh.ingest --query "cat:cs.CL AND abs:retrieval" --max-papers 45

Watch out: after re-indexing, the chunk texts change, so build a NEW test set (Section 7.2 Step 4) and compare all modes again on that new set. Comparing numbers measured on two different test sets is meaningless.

Watch out: keep data/eval_frozen.jsonl for a final check only. If you tune until the frozen set looks good, it stops being a fair test (you "overfit" to it).

Elite extension (optional): weighted RRF. OpenSearch's score-ranker-processor also accepts weights per query clause (the documentation shows 0.7 and 0.3) [15]. Try "combination": {"technique": "rrf", "rank_constant": 60, "parameters": {"weights": [0.4, 0.6]}} in PIPELINE_BODY (verify the exact field name in [15] for your OpenSearch version), run Step 3 and Step 4, and record it as experiment G.

CHECKPOINT: results.md has at least experiments A and C with their numbers, and you kept only changes that clearly helped.

If not: if python -m querymesh.search setup fails after your edit, the JSON in PIPELINE_BODY is broken: undo with Ctrl+Z and save.

SECTION 7.7 - Common mistake at this level

Mistake: trusting one number. A higher average hit@5 on 30 questions can be luck, and a pipeline can score well while being slow or citing the wrong paper.

How to spot it: you cannot say how many questions the number is based on, you changed two settings at once, or you measured on the same questions you tuned on. Fix: frozen test set, one change per experiment, report n, and always look at a few failing questions by hand, as every serious RAG paper does.

Second mistake: optimising retrieval alone. Look at cites gold paper and grounded rate (Section 7.4) together with hit@5: if retrieval improves but the end-to-end numbers do not, the bottleneck is in the grader or the writer.
